# Claude Code — 防幻觉设计深度分析

> 分析对象：`cc/src/` — 散布在 prompts / tools / services / utils 中的多层防幻觉机制
> 核心文件：`constants/prompts.ts` · `tools/FileEditTool/` · `tools/FileReadTool/` · `utils/file.ts` · `utils/bash/shellQuoting.ts` · `tools/AgentTool/prompt.ts` · `coordinator/coordinatorMode.ts`

---

 防幻觉设计核心要点总结：

  1. 工具约束即事实来源
  Claude Code 的核心哲学：模型无法直接访问文件系统，必须通过工具获取信息。每个 tool_result 形成可审计的事实链，模型的任何操作都基于实际工具返回结果，而非内部"记忆"。

  2. Read-Before-Write 强制门控
  FileEditTool / FileWriteTool 通过 readFileState 缓存追踪哪些文件已被实际读取。未读即编辑（典型幻觉行为）直接报错，且区分 isPartialView（部分读取也不允许编辑）。

  3. 精确字符串匹配作为 Grounding
  FileEditTool 的 old_string 必须在文件中精确存在。模型凭幻觉记忆的文件内容无法通过此检查。配合 findSimilarFile / suggestPathUnderCwd 纠正路径幻觉。

  4. Prompt 层面的多维禁令
  针对已知的高频幻觉类型（编造结果、伪造 Agent 输出、猜测 URL、虚构文档内容）设置明确的 prompt 指令，并标注为 False Claims Mitigation（FC rate 从 v4 的 16.7% 到 v8 的 29-30%，需特别对治）。

  5. 已知幻觉模式的硬编码修复
  对确定性幻觉（如 Windows >/dev/null 语法、API 消毒后的 XML 标签缩写）直接在代码中自动修正，不依赖模型自觉。

  6. 架构级不可伪造设计
  子 Agent 结果通过 task-notification 以 user 角色系统注入，主 Agent 无法自行生成该格式的消息。物理隔离保证结果的真实性。


## 一、整体防线架构

Claude Code 的防幻觉不是一个独立模块，而是分布在五个层次的纵深防御：

```
 Layer 5 | Prompt 指令层     — 禁止编造结果 / URL / Agent 输出 / 文档内容
---------+
 Layer 4 | 工具输入验证层   — Read-Before-Write / old_string 精确匹配 / 路径校正
---------+
 Layer 3 | 输入修正层       — desanitize / Windows nul 重写 / 引号归一化
---------+
 Layer 2 | 架构约束层       — tool_result 作为唯一事实源 / task-notification 系统注入
---------+
 Layer 1 | 时间戳校验层     — stale read 检测 / isPartialView 拦截 / 并发编辑防护
```

**设计理念**：**用工具的物理约束替代对模型诚实性的信任**。模型声称的任何事实如果没有对应的 tool_result，在架构上就不可能进入执行路径。

## 三、工具输入验证层 — Read-Before-Write

文件：`tools/FileEditTool/FileEditTool.ts` · `tools/FileWriteTool/FileWriteTool.ts`

### 3.1 readFileState 门控机制

```
FileEditTool.call(input)
  |
  +-- readTimestamp = readFileState.get(fullFilePath)
  |
  +-- !readTimestamp --> ERROR: "File has not been read yet. Read it first
  |                            before writing to it."
  |
  +-- readTimestamp.isPartialView --> ERROR: 同上
  |     （部分读取不算"已读"：offset/limit 读取无法确保模型看到完整内容）
  |
  +-- readTimestamp 存在 + 非 partial --> 继续
```

**设计原理**：模型最常见的幻觉之一是"凭记忆编辑文件"——用训练数据中见过的代码替代实际文件内容。强制 Read-Before-Write 确保模型在编辑前已经通过 FileReadTool 获取了文件的真实内容。

### 3.2 isPartialView 的语义

```typescript
// utils/fileStateCache.ts
type FileStateEntry = {
  timestamp: number
  content?: string       // 文件内容快照（用于 stale 比对）
  offset?: number        // 非 undefined = 部分读取
  limit?: number
  isPartialView?: boolean  // true = 只看了片段，不允许整体编辑
}
```

来源（标记为 isPartialView = true 的场景）：
- 附件注入的文件内容（可能与磁盘不一致）
- 带 offset/limit 的部分读取
- 内存/CLAUDE.md 文件加载

### 3.3 FileWriteTool 的平行机制

```
// tools/FileWriteTool/FileWriteTool.ts:199
if (!readTimestamp || readTimestamp.isPartialView) {
  ERROR: "This file already exists. Read it first before overwriting."
}
```

FileWriteTool 是全量覆盖，因此对幻觉的危害更大。同样强制已读。

## 四、工具输入验证层 — old_string 精确匹配

文件：`tools/FileEditTool/FileEditTool.ts` · `tools/FileEditTool/utils.ts`

### 4.1 核心校验流程

```
FileEditTool 校验 old_string:
  |
  +-- 1. 精确匹配：fileContent.includes(old_string) --> OK
  |
  +-- 2. 引号归一化：normalizeQuotes(searchString) vs normalizeQuotes(fileContent)
  |     找到索引后返回原文中的实际子串（保持原始引号形态）
  |
  +-- 3. 以上都失败 --> ERROR: "String to replace not found in file."
  |
  +-- 4. 多处匹配 + replace_all=false --> ERROR: "Multiple matches found"
```

**设计目的**：old_string 是 grounding anchor。模型必须提供文件中实际存在的字符串，这意味着它必须先读过文件才能编辑。这从根本上消灭了"凭想象编辑"的可能性。

### 4.2 引号归一化（有限容错）

```typescript
// utils.ts:73 findActualString()
function findActualString(fileContent: string, searchString: string): string | null {
  // 先尝试精确匹配
  if (fileContent.includes(searchString)) return searchString

  // 引号归一化后匹配（smart quotes -> straight quotes）
  const normalizedSearch = normalizeQuotes(searchString)
  const normalizedFile = normalizeQuotes(fileContent)
  const searchIndex = normalizedFile.indexOf(normalizedSearch)
  if (searchIndex !== -1) {
    return fileContent.substring(searchIndex, searchIndex + searchString.length)
  }

  return null  // 最终不匹配 -> 报错
}
```

容错边界严格：只处理引号类型差异，不做模糊/近似匹配。

## 五、路径幻觉纠正

文件：`utils/file.ts` · `tools/FileEditTool/FileEditTool.ts` · `tools/FileReadTool/FileReadTool.ts`

### 5.1 "Did you mean?" 机制

```
文件不存在时的纠正流程：
  |
  +-- suggestPathUnderCwd(fullFilePath)
  |     检测"丢失 repo 目录"模式：
  |     模型构建 /Users/X/src/foobar（不存在）
  |     实际是   /Users/X/src/currentRepo/foobar
  |     --> 返回带 repo 目录的正确路径
  |
  +-- findSimilarFile(fullFilePath)
  |     同目录下同名但不同扩展名的文件：
  |     模型写 foo.ts 但实际是 foo.tsx
  |     --> 返回 "Did you mean foo.tsx?"
  |
  +-- 都找不到 --> 报错 + 提示 cwd
        "File does not exist. Note: your current working directory is /path"
```

### 5.2 suggestPathUnderCwd 设计细节

```typescript
// utils/file.ts:228
async function suggestPathUnderCwd(requestedPath: string): Promise<string | undefined> {
  const cwd = getCwd()
  const cwdParent = dirname(cwd)

  // 只检查：路径在 cwd 的父目录下，但不在 cwd 本身下
  // --> 说明模型"忘了"repo 目录这一层
  if (resolvedPath.startsWith(cwdParentPrefix) && !resolvedPath.startsWith(cwdPrefix)) {
    const relativeFromParent = resolvedPath.slice(cwdParentPrefix.length)
    const suggestedPath = join(cwd, relativeFromParent)
    // 验证建议路径真的存在
    if (await fileOrDirExists(suggestedPath)) {
      return suggestedPath
    }
  }
}
```

**典型幻觉模式**：模型记住了用户目录结构但忘记了当前 repo 在路径中的位置。

## 六、已知幻觉的硬编码修复

### 6.1 Windows >/dev/null 幻觉（BashTool）

文件：`utils/bash/shellQuoting.ts:108-128`

```typescript
/**
 * The model occasionally hallucinates Windows CMD syntax (e.g., `ls 2>nul`)
 * even though our bash shell is always POSIX (Git Bash / WSL on Windows).
 * When Git Bash sees `2>nul`, it creates a literal file named `nul` -- a
 * Windows reserved device name that is extremely hard to delete and breaks
 * `git add .` and `git clone`. See anthropics/claude-code#4928.
 */
const NUL_REDIRECT_REGEX = /(\d?&?>+\s*)[Nn][Uu][Ll](?=\s|$|[|&;)\n])/g

export function rewriteWindowsNullRedirect(command: string): string {
  return command.replace(NUL_REDIRECT_REGEX, '$1/dev/null')
}
```

**背景**：模型在 POSIX 环境下偶尔产生 Windows CMD 语法，这不是随机错误而是可预测的幻觉模式（训练数据中两种语法混合）。硬编码修复而非靠 prompt 禁止。

调用点：`utils/shell/bashProvider.ts:127`
```typescript
const normalizedCommand = rewriteWindowsNullRedirect(command)
```

### 6.2 API 消毒标签的反向映射（FileEditTool）

文件：`tools/FileEditTool/utils.ts:526-550`

```typescript
/**
 * Contains replacements to de-sanitize strings from Claude.
 * Since Claude can't see any of these strings (sanitized in the API)
 * It'll output the sanitized versions in the edit response.

const DESANITIZATIONS: Record<string, string> = {
  '<fnr>':  '<function_results>',

```

**背景**：Anthropic API 在发送内容给模型前会消毒（sanitize）特殊 XML 标签（如 `<function_results>` -> `<fnr>`）。模型在 edit 时只能输出消毒后的缩写形式。`desanitizeMatchString()` 在 old_string 匹配失败时自动将缩写还原为完整标签再尝试匹配。

## 七、架构约束层 — 不可伪造的事实注入

### 7.1 tool_result 作为唯一事实源

```
整个 Agent 循环的事实链：
  模型输出 tool_use block --> 系统执行工具 --> tool_result 注入消息历史
                                            |
                                            +-- 模型无法跳过这一步
                                            +-- 模型无法修改 tool_result 内容
                                            +-- 历史中所有 tool_result 都是系统实际执行的结果
```

模型无法直接在消息历史中插入虚假的 tool_result，因为消息追加操作由 `query.ts` 循环控制（步骤 16: `state = { messages: [...messagesForQuery, ...assistantMessages, ...toolResults] }`），模型只能输出 assistant 角色的消息。

### 7.2 task-notification 系统注入

```
子 Agent 完成后：
  enqueuePendingNotification(task-notification XML)
    --> 以 user 角色注入主 Agent 消息队列
    --> 主 Agent 无法自行生成 user 角色消息
    --> 物理保证：通知内容来自实际子 Agent 执行

prompt 层面双重保险（AgentTool/prompt.ts:93）：
  "The notification arrives as a user-role message in a later turn;
   it is never something you write yourself."
```

### 7.3 tool_result 大小预算 + 磁盘溢出

```
工具返回超大结果时：
  结果 --> 写入临时文件（toolResultStorage.ts）
  模型收到 --> 预览（前 N chars）+ 文件路径
  需要完整内容 --> 必须调用 Read/TaskOutput 读取

防幻觉意义：
  模型无法"记住"超大输出的全部内容
  必须再次通过工具获取，形成可验证的读取记录
```

## 八、时间戳校验层 — Stale Read 防护

文件：`tools/FileEditTool/FileEditTool.ts:289-311`

### 8.1 修改时间校验

```typescript
// Check if file exists and get its last modified time
const lastWriteTime = getFileModificationTime(fullFilePath)
if (lastWriteTime > readTimestamp.timestamp) {
  // Timestamp indicates modification, but on Windows timestamps can change
  // without content changes (cloud sync, antivirus, etc.). For full reads,
  // compare content as a fallback to avoid false positives.
  const isFullRead = readTimestamp.offset === undefined && readTimestamp.limit === undefined
  if (isFullRead && fileContent === readTimestamp.content) {
    // Content unchanged, safe to proceed
  } else {
    return ERROR: 'File has been modified since read, either by the user
                   or by a linter. Read it again before attempting to write it.'
  }
}
```

### 8.2 三层校验逻辑

```
编辑前检查序列：
  1. readFileState 是否存在？            --> 否 = 未读，拒绝
  2. isPartialView？                     --> 是 = 部分读取，拒绝
  3. 文件修改时间 > 读取时间？
     +-- 是 + 完整读取 + 内容相同       --> 放行（Windows 误报处理）
     +-- 是 + 部分读取 或 内容不同      --> 拒绝（stale read）
  4. old_string 在文件中存在？            --> 否 = 幻觉内容，拒绝
```

**设计目的**：防止模型基于过时信息做编辑。场景包括：
- 用户在模型思考期间手动编辑了文件
- Linter/Formatter 自动修改了文件
- 另一个并发的子 Agent 修改了同一文件

## 九、Prompt 与代码的协同设计

### 9.1 Prompt 告知规则 + 代码强制执行

| 幻觉类型 | Prompt 指令（软约束） | 代码强制（硬约束） |
|---------|-------------------|--------------------|
| 凭记忆编辑文件 | "Read it first before writing" | readFileState 门控 |
| 编辑不存在的文件 | "Note: your current working directory is..." | ENOENT 检测 + Did you mean? |
| 编辑幻觉内容 | — | old_string 精确匹配 |
| 编造测试结果 | "Never claim all tests pass when output shows failures" | 无硬约束（依赖 prompt） |
| 伪造 Agent 结果 | "Never fabricate or predict fork results" | user 角色注入（物理不可伪造） |
| 猜测 URL | "NEVER generate or guess URLs" | 无硬约束（依赖 prompt） |
| Windows 命令语法 | — | rewriteWindowsNullRedirect() 自动修正 |
| API 消毒标签 | — | desanitizeMatchString() 自动还原 |

### 9.2 分层策略的互补性

```
有硬约束的幻觉类型（代码层可拦截）：
  --> prompt 作为额外提示（减少无谓的失败重试）
  --> 代码作为最终防线（即使 prompt 不遵从也安全）

仅有软约束的幻觉类型（只能靠 prompt）：
  --> 编造执行结果（无法在代码层验证文本真实性）
  --> 猜测 URL（无法判断 URL 是记忆还是推理得出）
  --> 这些依赖 False Claims Mitigation prompt + 用户审阅
```

### 11.2 第 1 层：Zod Schema 结构校验

```typescript
// toolExecution.ts:614
// 注释原文：surprisingly, the model is not great at generating valid input
const parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) {
  let errorContent = formatZodValidationError(tool.name, parsedInput.error)
  // ...
  return [{ message: createUserMessage({
    content: [{ type: 'tool_result',
      content: `<tool_use_error>InputValidationError: ${errorContent}</tool_use_error>`,
      is_error: true, tool_use_id: toolUseID }],
  }) }]
}
```

`formatZodValidationError` 将 Zod 错误转化为对模型友好的格式，区分三类问题：

| 错误类型 | 示例 |
|---------|------|
| 缺失参数 | `The required parameter 'file_path' is missing` |
| 多余参数 | `An unexpected parameter 'foo' was provided` |
| 类型不匹配 | `The parameter 'offset' type is expected as 'number' but provided as 'string'` |

延迟加载工具的特殊提示（`buildSchemaNotSentHint`）：

```
This tool's schema was not sent to the API -- it was not in the
discovered-tool set. Without the schema in your prompt, typed parameters
(arrays, numbers, booleans) get emitted as strings and the client-side
parser rejects them. Load the tool first: call ToolSearch with
query "select:ToolName", then retry this call.
```

**设计意图**：延迟加载工具的 JSON Schema 未随 API 请求发送，模型只能猜测参数格式。此时类型错误（如数组写成字符串）是预期行为，需要引导模型先通过 ToolSearch 获取 schema。

### 11.3 第 2 层：validateInput() 语义校验

Zod 只能检查结构，不能检查语义。22 个工具实现了各自的 `validateInput()`：

| 工具 | validateInput 检查内容 |
|------|---------------------|
| **FileEditTool** | 文件是否存在、是否已读（readFileState）、是否 partial view、stale read 检测、old_string 精确匹配、多处匹配检测、扩展名错误纠正（Did you mean?） |
| **FileWriteTool** | 已有文件是否先读、路径安全检查、团队记忆密钥守护 |
| **FileReadTool** | 路径存在性、是否为目录、page 参数对非 PDF 的拒绝 |
| **BashTool** | 命令语法验证、路径存在性 |
| **GlobTool / GrepTool** | 搜索路径存在性、suggestPathUnderCwd 纠正 |
| **NotebookEditTool** | .ipynb 存在性、cell 索引越界检测 |
| **SkillTool** | skill 名是否存在于已注册列表 |
| **SendMessageTool** | 目标 Agent 是否存在于 agentNameRegistry |
| **TaskStopTool** | task_id 是否对应实际运行中的任务 |
| **TaskOutputTool** | task_id 存在性、输出文件可读性 |
| **WebFetchTool** | URL 格式验证 |
| **WebSearchTool** | 查询非空验证 |
| **AskUserQuestionTool** | 问题和选项格式验证 |
| **ExitPlanModeTool** | 是否处于 Plan Mode |
| **ExitWorktreeTool** | 是否处于 Worktree |
| **CronCreate/Delete** | cron 表达式合法性、job ID 存在性 |
| **TeamCreateTool** | 团队配置合法性 |
| **PowerShellTool** | 命令语法验证 |
| **LSPTool** | LSP 服务器可用性 |
| **BriefTool** | 附件格式验证 |

`validateInput()` 与 `checkPermissions()` 的分工（来自 `Tool.ts:495` 注释）：

```
validateInput()    --> "这个调用在技术上能否执行？"（文件存在吗？索引越界吗？）
checkPermissions() --> "用户是否允许执行？"（权限规则、安全检查）
                       只在 validateInput 通过后才调用
```

### 11.4 第 3 层：内部字段防伪造

```typescript
// toolExecution.ts:756 — Defense-in-depth 注释
// _simulatedSedEdit 是权限系统内部注入的字段（SedEditPermissionRequest）
// 如果模型在输入中伪造它，可能绕过权限检查

if (tool.name === BASH_TOOL_NAME && '_simulatedSedEdit' in processedInput) {
  const { _simulatedSedEdit: _, ...rest } = processedInput
  processedInput = rest
}
```

### 11.5 校验失败的反馈设计

所有校验失败都以 `tool_result + is_error: true` 返回给模型：

```
结构校验失败：
  <tool_use_error>InputValidationError: FileEditTool failed due to the
  following issue:
  The required parameter `file_path` is missing</tool_use_error>

语义校验失败：
  <tool_use_error>File has not been read yet. Read it first before writing
  to it.</tool_use_error>

  <tool_use_error>File does not exist. Note: your current working directory
  is /path. Did you mean foo.tsx?</tool_use_error>

  <tool_use_error>String to replace not found in file.
  String: ...</tool_use_error>
```

**反馈设计原则**：
- 错误消息面向模型编写（LLM-friendly），而非面向人类
- 包含纠正建议（Did you mean?、Note: cwd is...）帮助模型快速恢复
- `is_error: true` 标记让模型知道需要重试而非继续

## 十二、生成后检测 — LSP 被动诊断与 Verification Agent

文件：`services/lsp/LSPDiagnosticRegistry.ts` · `services/lsp/passiveFeedback.ts` · `services/diagnosticTracking.ts` · `tools/AgentTool/built-in/verificationAgent.ts`

### 12.1 LSP 被动诊断系统

模型编辑/创建文件后，LSP Server 异步推送诊断信息，自动注入下一轮对话：

```
LLM 通过 FileEditTool 编辑文件
  |
  +-- clearDeliveredDiagnosticsForFile(fileUri)  清除旧诊断缓存
  |
  v
LSP Server（IDE 语言服务器：TypeScript/Python/Rust 等）
  |  异步推送 textDocument/publishDiagnostics 通知
  v
passiveFeedback.ts --> registerLSPNotificationHandlers()
  |  监听所有 LSP Server 的诊断通知
  v
LSPDiagnosticRegistry --> registerPendingLSPDiagnostic()
  |  注册 + 跨轮次去重（LRU 500 文件）
  |  按严重级排序（Error > Warning > Info > Hint）
  |  限流：每文件最多 10 条，总计最多 30 条
  v
attachments.ts --> getLSPDiagnosticAttachments()
  |  作为 attachment 注入下一轮 query
  v
模型在下一轮看到类型错误/语法错误 --> 自行决定是否修复
```

**局限**：依赖 IDE 环境中有 LSP Server 连接（VS Code/JetBrains 插件模式）。纯 CLI 模式下没有 LSP，此层不生效。

### 12.2 IDE 诊断追踪（基线对比）

```typescript
// services/diagnosticTracking.ts — DiagnosticTrackingService
beforeFileEdited(filePath)   --> 编辑前捕获基线诊断（通过 IDE RPC）
getNewDiagnostics()          --> 编辑后对比，只返回因编辑新增的错误
```

只报告**因 LLM 编辑引入**的新诊断，过滤掉编辑前就存在的错误。

### 12.3 Verification Agent — 内置只读验证子 Agent

```typescript
// tools/AgentTool/built-in/verificationAgent.ts
VERIFICATION_AGENT = {
  agentType: 'verification',
  background: true,                     // 后台异步执行
  disallowedTools: [                    // 严格只读
    FILE_EDIT_TOOL_NAME,
    FILE_WRITE_TOOL_NAME,

  ],

```

System prompt 中的自我反幻觉指令（129 行）：

```
You have two documented failure patterns:
  1. Verification avoidance — you find reasons not to run the check,
     read code, narrate what you would test, write "PASS," and move on.
  2. Being seduced by the first 80% — you see a polished UI or a passing
     test suite and feel inclined to pass it, not noticing half the buttons
     do nothing.

识别你自己的合理化倾向：
  "The code looks correct based on my reading" --> 阅读不等于验证，运行它。
  "The implementer's tests already pass"       --> 实现者也是 LLM，独立验证。
  "This is probably fine"                      --> "可能"不等于"已验证"。
  "I don't have a browser"                     --> 你检查过 MCP 工具了吗？

如果你发现自己正在写解释而不是命令，停下来。运行命令。
```

**触发方式**：非自动触发，需模型主动调用或用户使用 `/verify`。

### 12.5 生成后检测能力的真实边界

| 机制 | 检测什么 | 自动触发？ | 覆盖场景 |
|------|---------|-----------|---------|
| LSP 被动诊断 | 类型错误、语法错误、lint | 是（有 LSP 时） | IDE 模式 |
| IDE 诊断追踪 | 编辑引入的新错误（基线对比） | 是（有 IDE 时） | VS Code/JetBrains |
| Verification Agent | 功能正确性、边界、对抗性测试 | 否（需调用） | 所有环境 |
| PostToolUse Hooks | 用户配置的检查（lint/test） | 是（配置后） | 所有环境 |
| Prompt 指令 | 编造结果的诚实性 | 软约束 | 所有环境 |

**核心结论**：Claude Code 不做生成内容的语义级幻觉检测（不检查"代码逻辑是否合理"）。策略是预防（args 校验拦截幻觉输入）+ 外部验证器（LSP/Verification Agent 发现幻觉输出）。

## 十三、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 硬约束优先于 prompt | 代码强制 Read-Before-Write + 精确匹配 | Prompt 遵从率不可能 100%；硬约束保证即使模型忽视提示也无法造成损害 |
| 有限容错而非模糊匹配 | 只归一化引号和消毒标签，不做 fuzzy match | 过度容错会让幻觉内容"碰巧"通过检查；宁可报错让模型重读文件 |
| 路径纠正而非静默失败 | suggestPathUnderCwd + findSimilarFile | 纯报错会导致模型反复尝试错误路径；纠正建议帮助模型快速恢复 |
| Windows nul 硬编码修复 | 正则替换而非 prompt 禁止 | 可预测的确定性幻觉用代码修复效率最高；prompt 禁止可能干扰正常 Windows 开发场景 |
| False Claims 双向治理 | 同时禁止过度乐观和过度悲观 | 仅治过度乐观会让模型转向过度 hedging，降低有效信息密度 |
| task-notification 用 user 角色 | 系统注入而非 assistant 生成 | 利用 API 的角色约束（模型只能输出 assistant 消息）实现物理不可伪造 |
| isPartialView 拒绝编辑 | 部分读取不算"已读" | 模型可能基于片段推断整体内容并编辑未见部分，本质是幻觉 |
| stale read 内容比对兜底 | 时间戳 + 内容双重检查 | Windows 云同步/杀毒软件改时间戳但不改内容的误报问题 |
| Desanitization 机制 | 自动还原而非报错 | API 消毒是系统行为，模型输出缩写版是预期的，不应算作幻觉 |
| Zod safeParse + validateInput 两层分离 | 结构校验与语义校验正交 | Zod 处理类型/必填/多余字段（通用），validateInput 处理文件存在/已读/路径正确（工具特定） |
| 校验错误消息面向模型编写 | LLM-friendly 格式 + 纠正建议 | 目标是让模型自动恢复而非让人类调试；包含 Did you mean / Note: cwd 等上下文 |
| 内部字段双重防伪造 | strictObject（schema）+ 运行时剥离 | schema 是第一道防线，运行时剥离防 schema 退化时的安全回归 |
| Verification Agent 只读 + 自我反幻觉 | disallowedTools 硬限制 + prompt 识别合理化倾向 | 验证器自身也是 LLM，会有"读代码就说 PASS"的幻觉；prompt 专门列举 5 种合理化借口 |
| LSP 诊断限流 | 每文件 10 条 / 总计 30 条 / LRU 去重 | 防止大量诊断（如初次打开未格式化项目）淹没上下文窗口 |
