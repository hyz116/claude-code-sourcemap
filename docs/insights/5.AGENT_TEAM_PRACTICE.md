## 二、官方文档梳理(OBS)

### 与 subagent 的关键差异

| 维度 | Subagent | Agent Team |
|---|---|---|
| Context | 独立窗口,结果回主 agent | 独立窗口,完全独立 |
| 通信 | 只能向主 agent 报告 | teammate 之间可直接通信 |
| 协调 | 主 agent 全管 | 共享 task list + 自协调 |
| Token | 较低(结果汇总回主) | 较高(每个 teammate 独立 instance) |
| 适合 | 结果驱动的聚焦任务 | 需要讨论与协作的复杂工作 |

### 官方列出的 4 类适用场景(OBS)

1. 研究和评审(并行 lens)
2. 新模块/新特性(独立所有权)
3. 调试时多假设并行(类辩论)
4. 跨层协调(前/后/测试各管)

官方原文还说:"add coordination overhead and use significantly more tokens"——agent team 在**协调成本和 token 成本上都显著更高**,sequential / 同文件编辑 / 多依赖任务用单 session 或 subagent 更合算。

### 官方明列的限制(OBS,逐项被本次执行印证)

- "Task status can lag" — 我们撞到了,本文 §六详述
- "`/resume` 不恢复 in-process teammates" — 本次未触及
- "One team at a time per lead" — 本次未触及
- "No nested teams" — 本次未触及

### Token 成本(OBS + 推论)

官方说 token "scale linearly with teammate count"。换算到本次:4 个 teammate ≈ 4 倍单 session 成本(粗略)。本次用 ~12 min 拿到 ~1100 行实证产出 + 7 处纠错——主观判断 ROI 成立(SPEC,因为没有"单 session 顺序做"的对照测量)。

## 三、案例:leto-risk wiki 改进 P0-P3(OBS-heavy)

### 输入

leto-risk 是 7 模块 Java 风控系统的代码库,经过前序对话的反思识别出 4 项 wiki 改进:

- **P0**: 创建意图导航文档 `docs/TAXONOMY.md`(读 ~15 份文档 + 综合 + 实证锚点)
- **P1**: 7 模块 chuye-doc/INDEX.md 审计(协议合规检查)
- **P2**: 跨模块 insight 文件 3 篇(每篇深读 seed sources + grep 验证 + 写 80-150 行)
- **P3**: 修改另一个 repo 的 pattern doc(增量 ~40 行)

4 个任务**文件域不重叠**(避免冲突)、**类型为 review/synthesis**(不是 implementation)、**有自然并行性**。

### 决策

- 4 个 teammate(在官方推荐 3-5 区间)
- 全部用 `general-purpose` agent type
- 每个 brief **自包含**(因为 teammate 不继承 lead conversation history)
- TaskCreate 4 个 P 任务做 visibility,但任务描述也直接写在 prompt 里(不依赖 agent 主动 claim)
- 没用 plan approval、没用 hooks、没用 subagent definition

### 实测

时间线(本会话观察,OBS):

```
02:14 spawn 4 teammates 完成
02:14 P1 完成(index-auditor,最快任务)
02:17 P0 完成(taxonomy-builder)
02:20 P3 完成(pattern-feedback)
02:26 P2 完成(insight-elevator,瓶颈)
─────────────────────
墙钟总时长 ≈ 12 分钟
```

产出体量:

| 任务 | 产出 | 体量 |
|---|---|---|
| P0 | TAXONOMY.md | 133 行,15 条意图条目 |
| P1 | INDEX.md 修正 | 1 处补登记 + 删冲突段 |
| P2 | 3 篇 insight | 257+285+335=877 行 |
| P3 | pattern doc 增量 | +44 行 |
| **总** | | ~1100 行新文档 + 7 处事实纠错 |

### 关键观察:7 处事实纠错的来源(OBS)

| # | 来源 | 内容 |
|---|---|---|
| 1 | pattern-feedback grep | lead brief "系统全景 ~280 行" → 实测 179 |
| 2 | insight-elevator grep | leto-meta "17 个 ConfigService" → 实测 16 |
| 3 | insight-elevator grep | "`#t` 后缀 indi+nl" → 实证 nl 子模块 0 命中 |
| 4 | insight-elevator 读代码 | 漏 `isTestRun` 是第 4 个独立 test 概念 |
| 5 | insight-elevator 读代码 | "6 个后缀"实为异质归类(3 真后缀 + 控制信号 + 业务字段 + schema 字段) |
| 6 | insight-elevator hedge | engine→disposal/streamhouse topic 配置未对比 |
| 7 | index-auditor 读协议 | server INDEX「备注」段与根协议直接冲突 |

注意结构:**5/7 来自同一个 agent**(insight-elevator)。下一节讨论这件事的解释。

## 四、机制猜测:多解释并列(INF/SPEC)

> 本节主动应用 [research-synthesis-bias-checklist](../../../.claude/projects/-Users-huangyuze-Documents-Mine-GitHub-open-source-claude-code-sourcemap/memory/) 的偏差检查。Trip wire:任何写起来 quotable 的归因都先停下检查。

**现象**:4 agent 并行执行严格实证 brief,产生 7 处事实纠错,**包含 lead 的承袭错误**(数字、概括、协议冲突)。

**对这件事可能的解释**:

### 解释 A:并行 cross-check(原始直觉,部分成立)

agent 间互相校验各自 brief 的事实声明。

**反驳**:7 处纠错里 5 处来自同一 agent (insight-elevator),不是"agent A 校 agent B 的 brief"。**真正的 cross-check 只有 1 处**(index-auditor 用根协议校验自己的 brief 局部约定)。

### 解释 B:实证纪律本身就够,并行不是必要条件(强反例)

如果让 1 个 agent 顺序做 4 个任务,只要每个任务都有强实证 brief,可能也能抓出大部分错。

**反驳**:这个反例无法直接证伪——我们没做对照实验。但**有间接信号**:之前 lead 自己写 chuye-doc 时也有强实证纪律,仍出现"head 截断没 wc -l 补"、"~70/~80 编造数字"这类错误(详见 leto-risk `docs/log.md` line 22)。**强实证 + 单 agent ≠ 总能抓到 lead 的承袭错误**——lead 自己是 agent 时存在自我盲点。

### 解释 C:任务类型适合产生纠错(任务驱动而非 team 驱动)

P0-P3 全是"读多份文档 → 综合"类任务,grep / wc / 实证锚点是天然动作。**可能换成 implementation 类任务,纠错率会大幅下降**——团队形态本身的贡献被高估。

**反驳**:N=1,无法对比 implementation 类任务的纠错率。

### 当前判断(commit + hedge)

- **A 部分成立**(7 处中有 1 处真 cross-check)但不是主因
- **B 不能完全排除**——单 agent 高纪律可能也能拿到大部分纠错
- **C 不能排除**——任务类型贡献可能远大于 team 形态贡献

**最诚实的归因**(SPEC):"这次 4 agent 并行执行的纠错率 = 任务类型适合实证 × agent 各自纪律到位 × 第三人称视角对 lead brief 的天然怀疑"。**不能简单归因为"team 模式 = cross-check"**——这是 N-mechanisms-to-philosophy 偏差。

> Trip wire 触发:此前我自己写过"team 真正价值是双向校准"——重读发现这是**听起来 quotable 但 over-extrapolation** 的归纳。本文降级为"在这次任务上,纪律 × 并行 × 第三人称视角共同产生纠错效果,N=1 不足以归纳为通则"。

### 一个稍微更安全的提法(INF)

**第三人称视角的诚实门槛**(INF,这次有支持):**当一个声明从 lead 主观转移到 agent 客观时,实证纪律的边际效果会被放大**。lead 自己写时容易"凭印象/承袭",因为压力都在产出;agent 拿到 brief 后,产出压力转移到了 agent,而 brief 变成了被验证的对象。这是机制猜测,不是定论。

## 五、Brief 写法模板

实测有效的结构(本次 4 份 brief 的共同骨架)。仅作为起点,不是规范。

```markdown
You are joining team "<team-name>" as <role>. Your task is <P-id>: <one-line goal>.

## Context (你不知道这件事 — 我briefing你)

<给 agent 完整背景:任务为什么重要 / 历史决策 / 已知约束>

## Your deliverable

<一句话最终产出>

## Concrete steps

1. **Read for X**: 列具体文件路径
2. **Synthesize Y**: 列具体输出格式
3. **Register**: 登记到哪个 INDEX
4. ...

## Constraints

- 实证纪律(grep / wc -l / 命名推断必须 hedge)
- 不要 X / Y / Z
- 体量限制

## Reporting

Reply with: <具体格式>。

Today's date: YYYY-MM-DD.
```

### 关键技巧(INF,从这次实测提炼)

1. **"You don't know this — I'm briefing you"** 显式提醒 agent 它没有 lead 的对话历史。否则它可能假设有共享上下文(实际没有)
2. **任务 step 用具体动词 + 文件路径**,不用抽象描述
3. **报告格式 explicit**,否则 agent 报告千奇百怪难聚合
4. **"实证纪律"段是关键**——明确告知"如果 grep 发现 brief 有错优先纠错不要按错的写"。本次 7 处纠错与这条 prompt 提示直接相关
5. **`Today's date`** 要写——agent 需要写 log 行的日期

## 六、State machine 坑(OBS,本次实测)

### 坑 1:TaskUpdate 触发 idle agent 重新激活

我做 `TaskUpdate(owner="agent-name")` 试图显式分派任务给已经在跑的 agent,触发了 agent 收到"任务派发通知"重新激活,造成 idle notification 反复刷屏。

**修法**:已 spawn 的 agent 不要再修改 task ownership,信息直接放 prompt 里就够。task list 仅作为 lead 视图的进度显示。

### 坑 2:shutdown_request 必须 lead 主动发,否则 TeamDelete 失败

`TeamDelete` 在 active members 存在时会失败。系统提示"don't originate shutdown_request unless asked"是给 teammate 看的,**lead 关闭已完成工作的 teammate 是合理职责**。

### 坑 3:Task 自动完成不可靠(官方明文承认)

官方原文:"Task status can lag: teammates sometimes fail to mark tasks as completed"。本次实测证实——agent 完成工作汇报给 lead,但 task 状态没自动转 completed,需要 lead 手动 TaskUpdate。

**修法**:lead 接收 agent 报告后,手动确认 task completed 是正常工作流的一部分,不要预期自动化。

### 坑 4:Spawned agent 不会自动 claim 现有 task

agent 是按 prompt 工作的,不主动看 task list。如果不在 prompt 里告诉它"task #N 是你的",它不会去 update task #N 的状态。

**修法**:要么(a)spawn 后再发一条 SendMessage 告诉它 task ID,要么(b)直接放弃 agent 自动 claim,task list 作为 lead 视图。我选了 (b)。

## 七、何时该用 / 何时不该用(决策框架)

综合官方建议 + 这次实测,**本框架仅适用于和这次类似的 review/synthesis 任务**(SPEC,N=1):

### 该用的信号

- 任务可拆分为 ≥ 3 个**文件域不重叠**的子任务
- 每个子任务都需要"读多份源 + 综合"——而不只是一次性查找
- 实证纪律重要(产出会被引用 / 错误代价高)
- 主对话上下文已经较满,不能再吃下子任务的 tool 输出
- 子任务之间**不需要先后衔接**

### 不该用的信号

- 任务有强先后依赖(用 sequential 单 session)
- 多个 agent 会改同一文件(用 sequential 或 worktree)
- 任务量小(< 1 子任务体量),并行收益 < 协调成本
- 任务是 implementation 类(本文 N=1 没覆盖此场景,无据可断)
- 不愿意承担 ~4× token 成本(官方明示)

### 中间态

- 任务可并行但没那么多 — subagent(轻量,结果回主)更合适
- 任务并行且需要互相讨论(辩论 / 多假设) — 用 team 但要主动设计"互相挑战"机制(官方原话:"have them try to disprove each other's theories")

## 八、与其他工具的边界

| 工具 | 用什么时候 |
|---|---|
| 单 session | 默认,大部分任务 |
| Subagent | 想并行但不需要互通,只要结果(token 省) |
| Agent team | 子任务 ≥ 3 + 文件域不重叠 + review/synthesis 类(本文 N=1) |
| Git worktrees | 想自己手动跑多 session,不要自动协调 |

注意:**这 4 个不是替代关系而是工具光谱**。"该用 team 还是 subagent"在边界附近的判断主要看是否需要**teammate 间通信**(team)还是只要**结果回主**(subagent)。

## 九、本观察的局限(NARR + SPEC)

- **N=1**:本文核心数据来自单次执行(P0-P3),没有跨任务、跨用户、跨任务类型对比。任何"agent team 适合 X"的断言都有 N=1 风险
- **任务偏 review/synthesis**:对 implementation 类任务、debug 类任务、多假设辩论任务的适用性**没有数据支持**——官方文档说有用,本文没复核
- **观察者偏差**:这次 lead 是我自己,我对自己 brief 错误的判断有偏见——可能高估了"agent 抓到 lead 错误"的价值,因为我是被纠错的人,会自然倾向"这个机制有用"
- **Lead 模型可能影响判断**:lead 是 Opus 还是 Sonnet,brief 质量、调度判断、纠错接受度都不同。本文是 Opus lead,Sonnet/Haiku lead 的 ROI 可能不同
- **"实证纪律"是 prompt-induced,不是 team 形态本身的属性**:如果 brief 里不写"实证纪律严格"指令,agent 不会自动 grep / wc。本文 7 处纠错很大程度是 prompt design 的功劳,**不能算 team 形态的红利**
- **"7 处纠错"是 outcome,不是 process metric**:换 4 个不同任务、不同 lead 写不同 brief,纠错数可能从 0 到 20。这个数字不稳定,不能当 KPI

## 十、一句话(谨慎)

**这次实证支持的命题**(限定于 review/synthesis 任务、Opus lead、强实证纪律 brief):

> 4 个并行 agent 在严格实证 brief 下,12 min 内产出 ~1100 行新文档 + 7 处事实纠错,主观 ROI 成立。**主要的红利来自 prompt 里的实证纪律,team 形态提供了让多个独立 agent 同时执行该纪律的载体——但 team 形态本身不等于纠错能力**。

> 不要把这条扩展为"agent team 总是值得",也不要扩展为"team 的本质是 cross-check"。N=1。
