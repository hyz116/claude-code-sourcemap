## 元假说：我观察到的一个统一姿态（不一定是 Anthropic 的）

把 24 篇 concept 页放一起看，**我归纳出**这样一个 framing：

> **不信任 LLM 的诚实性，但充分利用 LLM 的判断力。设计的工作是构建一个让 LLM「想做坏事也做不到」的物理框架，同时让「想做好事时」推理负担最低。**

⚠ 这句话很 quotable，但它是**我的归纳**——Anthropic 设计师可能从未用这种语言描述自己工作。他们内部可能：
- 用完全不同的概念框架（每个子系统独立设计，没有"姿态"）
- 在某些机制上违反这条（如 [[predictable-hallucination-hardcode]] 的 client 端悄悄修改）
- 没有把它作为有意识的指导方针

把它当**有用的描述性假说**——帮助你**理解**Claude Code 的设计倾向，但不是**定律**。

## 五个假说簇

> ⚠ 下面每条带"原则"或"论点"标签的内容都是**事后归纳的口号**，不是 Anthropic 文档里的指引。每条结构：
> - **论点** = 我提炼的一句话——质量取决于我归纳得对不对
> - **直觉** = 我编的解释为什么这条成立
> - **实例** = 真实的（OBS）—— 这部分可信
> - **迁移配方** = 我的建议——你自己场景验证
> - **反 pattern** = 我的对照——也是建议
>
> **可信度**：实例 > 迁移配方 > 论点 > 直觉。读的时候按这个顺序倒着 sanity check。

### 簇 1：信任与防御

#### 1.1 物理约束 > Prompt 约束

**论点**：Prompt 让 LLM "不要 X" 不是不可能但**不可靠**；架构让 LLM "无法 X" 才稳。

**直觉**：Prompt 遵从率永远 < 100%。但 API 角色约束（assistant only）、工具集过滤、tool_result 不可伪造这种**架构层强制**是 100% 的。

**实例**：
- [[ground-truth-via-tools]]：tool_result 是唯一事实源——LLM 物理上无法伪造
- [[task-notification-injection]]：子 Agent 结果用 user 角色注入，主 Agent 物理无法生成
- [[read-before-write]]：readFileState 缓存门控——未读不让写
- VerificationAgent 的 `disallowedTools` 物理禁掉 Edit/Write

**迁移配方**：每次想用 prompt 禁止某个行为时，问"能不能用工具集 / 角色 / 状态机让它做不到"。能就用架构。

**反 pattern**：把 "请不要 X" 写在 system prompt 顶上，期望 LLM 100% 服从。

#### 1.2 Fail-Closed 优于 Fail-Open

**论点**：不确定的输入 / 状态 / 解析结果，**默认拒绝并问用户**——绝不放行。

**实例**：
- [[bash-command-classification]]：tree-sitter AST 任何未知节点 → too-complex → ask user。"we never interpret structure we don't understand"
- [[tool-args-prevalidation]]：Zod strictObject + 任何意外字段 → reject
- [[predictable-hallucination-hardcode]]：semanticNumber 只接受严格数字字面量，其他 fall-through 报错

**迁移配方**：解析器面对**自己模型外的输入**默认拒绝。**绝不写 catch-all 兜底**——那让攻击者借未识别路径绕过检查。

**反 pattern**：`z.coerce.boolean()`（`Boolean("false") === true`）、`try { parse } catch { return defaultValue }`。

#### 1.3 拒绝宽松解析

**论点**：标准库的"宽容"模式（`z.coerce.*` / `lodash.toNumber`）会让真错误**碰巧通过**。**自己写精确正则**比借用宽松库安全。

**实例**：
- [[predictable-hallucination-hardcode]]：semanticNumber 用 `/^-?\d+(\.\d+)?$/`，而不是 `Number(v)`
- [[bash-command-classification]]：normalizeQuotes 仅归一化引号一种偏差，不做模糊匹配——"过度容错会让幻觉内容碰巧通过检查"

**迁移配方**：边界处的修复必须有**显式枚举**。"我接受这 5 种已知偏差，其他报错"——这种声明远胜过"尽力 coerce"。

#### 1.4 多层 Gate 收紧实验

**论点**：新功能 / 实验性 API 应该层层 gate 启用，而不是一刀切打开。

**实例**：
- [[prompt-cache-editing]]：5 层 gate（feature DCE → GrowthBook flag → firstParty → main-thread → 模型白名单）
- [[plan-verification-handoff]]：3 层 DCE（feature flag / USER_TYPE / 字面量比较）

**迁移配方**：新功能用 `feature flag → user gate → role gate → context gate` 逐层放开，每层独立可关。

#### 1.5 修复对模型不可见

**论点**：客户端边界处的修复（desanitize、Windows nul rewrite、smart quote 归一化）**不污染模型对正确输入的认知**——schema 仍声明正确类型，模型不应被告知"我们悄悄帮你修了"。

**实例**：
- [[predictable-hallucination-hardcode]] 6 个样本——desanitize / normalizeQuotes / semanticNumber 全部 client-side coercion，invisible to API schema
- `z.preprocess` 不影响 emit 给 API 的 schema

**迁移配方**：修复是**单向客户端兜底**，不写回 prompt / schema / 错误消息。模型应该按"正确接口"的认知工作，修复只是过渡保险。

### 簇 2：信息流设计

#### 2.1 状态外部化 + 多层恢复

**论点**：关键状态（plan 内容、对话历史、待办列表）**不只放内存**。外部化到磁盘 + 多层 fallback 让 crash / resume / 外部编辑不破坏会话连续性。

**实例**：
- [[plan-mode-state-machine]]：plan 文件 3 层恢复（文件 → file snapshot → message history）
- [[result-delivery-guarantee]]：6 层交付保障
- [[context-compression-cascade]]：autocompact summary 附 transcriptPath 让模型能查原文

**迁移配方**：识别会话里"丢了就破"的状态——存到 KV / 文件，至少 2 层 fallback。

#### 2.2 多层防御按"输入/中间/输出"切分

**论点**：防御不是单点，而是分布在数据流各层。**输入层防止异常进入**、**中间层维持事实链**、**输出层治理汇报姿态**——三层互不替代。

**实例**：
- 输入层：[[read-before-write]] / [[tool-args-prevalidation]] / [[bash-command-classification]] / [[predictable-hallucination-hardcode]]
- 中间层：[[ground-truth-via-tools]] / [[task-notification-injection]] / [[result-delivery-guarantee]]
- 输出层：[[false-claims-bidirectional]] / [[post-generation-verification-channels]]

**迁移配方**：画出系统数据流，识别 LLM 接触的每一层；每层独立设计防御点。**不要让某一层"兜底"全部**。

#### 2.3 事件锚点 vs 全局锚点

**论点**：Reminder / 节流 / 触发判定**应该绑定具体事件**（plan_mode_exit、上一次 snip）**而非全局计数**。事件锚点保证语义清晰、跨 session 可恢复。

**实例**：
- [[plan-verification-handoff]]：reminder 计数从 plan_mode_exit attachment 起算，不是 session 全局
- [[context-compression-cascade]]：context efficiency nudge 锚到 snip 边界 / compact 边界

**迁移配方**：写"每 N 轮提醒一次"前先问"N 从什么时刻起算"。如果是"session 开始"通常错——应该是某个具体业务事件。

#### 2.4 跨级显式数据流

**论点**：当下游级别需要知道上游做了什么，**显式传递信号**——不要让下游自己去算或猜。

**实例**：
- [[context-compression-cascade]]：snipTokensFreed 显式传给 autocompact
- [[tool-args-prevalidation]]：backfillObservableInput 显式分流"观测 input vs 执行 input"
- [[prompt-cache-editing]]：cacheDeletionsPending 显式标记"合法 cache miss"

**迁移配方**：每次某个组件的行为依赖另一个组件刚做了什么，加个显式参数 / state 字段传它。"自己算"通常会漏。

### 簇 3：LLM 协作

#### 3.1 节流 > 每轮提醒

**论点**：LLM 看到**重复**提醒会忽略；间歇性提醒效果更好。10-30 轮的节流间隔比每轮硬提醒驱动行为效果显著。

**实例**：
- [[plan-verification-handoff]]：每 10 轮提醒一次
- [[flag-vs-hardcode]] 的 nudge：在 loop-exit 唯一时机注入
- [[context-compression-cascade]] 的 reminder：每 N tokens 一次

**迁移配方**：任何"提醒模型做 X"的机制都应该有节流——参数应该 A/B 测，不是拍脑袋。

**反 pattern**：每轮都把"请记得做 X"塞进 system prompt——LLM 会脱敏。

#### 3.2 委托不能转移理解

**论点**：让 LLM "based on findings" / "use the previous results" / "fix the bug from earlier" 是**懒委托**——最终它会胡乱处理，因为它没真的读懂。

**实例**：
- [[coordinator-mode]]：'Never write "based on your findings" or "based on the research."'
- [[plan-verification-handoff]]：'directly (NOT the Agent tool or an agent)'
- [[false-claims-bidirectional]]：'you cannot self-assign PARTIAL by listing caveats'

**迁移配方**：每次 prompt 里出现"基于上面/之前/...的结果"，停下，**亲自总结成具体内容**写进 prompt。理解必须在你这里发生，不能转移给下游 Agent。

**反 pattern**：`"Based on the analysis above, fix the bug"` 这种 prompt——下一个 worker 没看到上面的对话。

#### 3.3 信息密度 > 防御性

**论点**：让 LLM 输出"已确认就明说"，不要 hedging。**双向治理**——既禁过度乐观（false claims）也禁过度悲观（hedging）。

**实例**：
- [[false-claims-bidirectional]]：完整原则
- VerificationAgent 契约：'PARTIAL is for environmental limitations only — not for "I am unsure"'

**迁移配方**：评测 LLM 输出时**同时统计** false-claim rate 和 hedge rate。仅治一边会推它转向另一边。

#### 3.4 错误消息面向 LLM 设计

**论点**：工具校验失败时，错误消息**为模型 retry 设计**，不是为人类调试。包含"为什么错 + 怎么修 + 上下文"三件套。

**实例**：
- [[tool-args-prevalidation]]：`<tool_use_error>InputValidationError: ... Did you mean foo.tsx? Note: cwd is /path</tool_use_error>`
- [[bash-command-classification]] 失败给"这是哪类危险模式"加纠正建议

**迁移配方**：现有"面向人类"的报错（`Validation failed at line 42`）改成"面向 LLM retry"（`The 'amount' field must be a positive integer; received '1.5'. Use Math.floor() or specify in cents.`）

### 簇 4：演化与实验

#### 4.1 Magic Numbers 必附理由

**论点**：所有阈值 / buffer / 限流参数**注释里必须写为什么是这个数**——empirical 实测、事故响应、还是模型行为。

**实例**：
- `MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000` // Based on p99.99 of compact summary output being 17,387 tokens.
- `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3` // BQ 2026-03-10: 1,279 sessions had 50+ consecutive failures...wasting ~250K API calls/day globally.
- `False-claims mitigation for Capybara v8 (29-30% FC rate vs v4's 16.7%)`

**迁移配方**：每次写一个 `const N = 10` 类参数，问自己"这是怎么得到的"，写进注释。**没数据就标"untested guess"——诚实**。

#### 4.2 默认值是冷启动专用，不是继承专用

**论点**：同一个 alias / 配置 / 默认值**在不同语境下应该解析成不同东西**。"用户首次说 X" vs "子组件想跟父保持一致" 不能用同一个 default。

**实例**：
- [[alias-tier-inheritance]]：bare `opus` alias 在子 Agent 应该复用父字符串而非走 provider default
- [[opusplan-tradeoff]]：opusplan 静态展开是 Sonnet，但 plan + 不超 200K 时动态升 Opus

**迁移配方**：检查所有 default value 用了几个语境。**冷启动**（用户首次配置）vs **继承**（子模块想跟父一致）vs **fallback**（其他全失败时兜底）应该 3 种 path，不是 1 个 default。

#### 4.3 观测的合法/非法分类

**论点**：监控系统会对所有"异常"告警。**合法异常**（cache_edits 导致的 cache miss、autocompact 后的 token drop）必须打标避免误报。

**实例**：
- [[prompt-cache-editing]]：`cacheDeletionsPending` 标记
- [[post-generation-verification-channels]]：IDE diagnostic 只报"因这次编辑新增的"——过滤掉编辑前已存在的错误

**迁移配方**：监控告警上线时同步设计 "expected anomalies" 标签。任何会主动让 metric 变化的操作都该标——否则 oncall 被噪音淹死。

#### 4.4 Tool 实现可分离，wire-up 必须保留

**论点**：实验功能的实现可以 DCE 删掉，但**接口面**（状态字段、属性钩子、attachment 路径）应保留——避免 wire-up 漂移。

**实例**：
- [[plan-verification-handoff]]：3P 包里 VerifyPlanExecutionTool 不存在，但状态字段 / reminder 路径 / auto-allowlist 全保留

**迁移配方**：插件式架构里，**接口面跟实现解耦**——核心实现可换，接口面稳定。让"启用功能"只需 link 实现。

### 簇 5：复杂度管理

#### 5.1 代价/失真梯度排序

**论点**：处理压力时**先尝试便宜的方案**，能解决就停。多级方案按"近零成本 → 昂贵成本"排序，每级失败才升级到下一级。

**实例**：
- [[context-compression-cascade]]：4 级压缩（snip / microcompact / collapse / autocompact）
- [[multi-tier-degradation]]：失败恢复同模式

**迁移配方**：任何"满了 / 不行了 / 失败了" 处理路径写成 N 级——按代价从低到高。**不要直接跳最贵的**。

#### 5.2 弱启发式有意识地弱

**论点**：某些拦截 / 检查 / 提醒**故意做得宽松**——宁可漏假阴，不要假阳。强约束在别的层做。

**实例**：
- [[flag-vs-hardcode]] 的 verification nudge：`/verif/i.test(content)` 故意用 regex 而非语义检查——主防线在 system prompt 契约
- [[bash-command-classification]] AST 路径不解释未知节点，但**不试图覆盖所有 bash 语法**

**迁移配方**：当你发现某条规则"覆盖率不够"时，**先问它是不是主防线**。如果不是，弱启发式可能就是最优——别强求完美。

#### 5.3 单一谓词跨多功能

**论点**：架构里"主线程 vs 子组件" / "用户 vs 系统" / "首次 vs 重新"这种**核心边界**应该用**单一谓词**判定，多功能复用同一谓词。

**实例**：
- `!context.agentId` 在 8+ 处复用：autocompact / queue routing / verification nudge / Plan Mode 入口 / ...
- 引入新功能想区分"主线程"无需自己定义判定，自动对齐

**迁移配方**：识别系统的核心边界（主/子、内/外、首次/重复），用一个谓词建模。**新功能想区分这条边界时复用**，不是自己重新定义。

#### 5.4 ML 兜底，结构化主路径

**论点**：用 LLM 做决策**不应该在主流程上**——结构化检查 / 规则匹配是主菜，LLM 是甜品。

**实例**：
- [[bash-command-classification]] 的 ML 分类器在 ant-only build；3P 完全靠 AST + 白名单 + 规则
- [[prompt-cache-editing]] 5 层 gate 全是结构化判断
- [[post-generation-verification-channels]] LSP / hooks / Verifier 各自独立，LLM Verifier 只是其中一通路

**迁移配方**：每次想用 LLM 做决策，先问"能不能用结构化检查 / 规则解决"。能就用结构化。LLM 是兜底。

#### 5.5 用户配置作为开放扩展点

**论点**：作为系统设计者**承认自己不知道**用户的 stack——开放钩子让他们自己加检查 / 修复 / 验证。

**实例**：
- [[post-generation-verification-channels]] 第 ④ 通路：PostToolUse hook（用户自己配 `eslint --fix $FILE`）
- [[tool-args-prevalidation]] 第 ⑥ 步：PreToolUse hook（5 类返回值让用户介入）

**迁移配方**：在系统的关键 lifecycle 点（前置 / 后置 / 错误 / 完成）开放 hook。**不要假设你知道用户的 stack**——给他们开口子，自己决定挂什么。

## 反 Pattern 速查

| 反 Pattern | 出现处 | 替代 |
|---|---|---|
| `try { parse } catch { return null }` | 任何容错代码 | Fail-closed + 显式枚举 |
| `z.coerce.boolean()` / `Number(v)` | 类型转换 | semanticNumber / semanticBoolean 精确正则 |
| `"Based on your findings, fix the bug"` | Sub-agent prompt | 亲自 synthesize 后写完整 spec |
| `"All tests pass"` 当存在 failure | 报告输出 | 报具体数字 "5 passed, 3 failed" |
| 每轮 system prompt "请记得做 X" | 提醒机制 | 状态机 + 节流 attachment |
| 单一 default 跨"首次 / 继承 / fallback" | 配置系统 | 区分语境，不同 default |
| Magic number 没注释 | 任何阈值 | 注释里写理由（empirical / 事故 / 推算）|
| `if (!context.someState) ...` 多个独立判断 | 边界判定 | 单一谓词跨多功能复用 |
| LLM 做主流程决策 | 任何架构 | 结构化主路径 + LLM 兜底 |
| 监控不区分合法/非法异常 | 观测系统 | 操作侧标 expected anomalies |

## 我归纳出的 3 条"贯穿线"（高 NARR 风险）

⚠ 下面 3 条是我**最 quotable 的提炼**，也是**最可能误导**的部分。它们把"24 篇里能看到这种模式"**升级成**"Claude Code 是这样设计的"——这是不严谨的。**带最高怀疑读**。

### 线 1：物理 > 诚信（伪)

我的归纳：不指望模型自觉，用架构让它做不到。Tool 不可伪造、读取门控、AbortController 三层、disallowedTools 物理隔离——看起来一以贯之。

**反例 / 削弱**：
- [[predictable-hallucination-hardcode]] 走相反方向——client 端**悄悄修改**模型的输入和输出，相当于"信任修复结果"而非物理隔离
- [[false-claims-bidirectional]] 完全是 prompt 层的诚信治理——没有物理约束

**结论**：这条**部分成立**。在某些子系统里很显著（防消息历史伪造），在其他子系统不存在或反向。

### 线 2：明确 > 含糊（中度可信）

我的归纳：每个数字附理由、每个 default 标语境、每个状态字段写定义、每个 prompt 禁 lazy delegation——拒绝模糊地带。

**支持证据**：Magic numbers 注释里附数据（如 `MAX_OUTPUT_TOKENS = 20_000` 来自 p99.99 实测）确实是真实模式，多处出现。

**削弱**：但很多代码里也有未注释的 magic numbers / 含糊的 fallback。Claude Code 整体并非"零模糊"——只是**某些关键参数**附了理由。我把"部分明确"夸大成"全面明确"。

### 线 3：分层 > 单点（最可信但最缺乏说服力）

我的归纳：防幻觉 4 层、压缩 4 级、降级多 tier、5 通路验证——没有单点，每个失败模式都有专属一层处理。

**真实部分**：分层防御确实是观察到的模式，多处出现。

**问题**：这是**任何成熟系统的通用属性**，不是 Claude Code 独特的。把它列为"贯穿线"反而稀释——任何 banking app / 操作系统 / 大型 web 服务都符合。**作为 Claude Code 的辨识特征价值不高**。

**校准后的版本**：

| 原"贯穿线" | 校准后的描述 |
|---|---|
| 物理 > 诚信 | 在**消息历史 / 工具门控**层面成立；prompt 层和输入修复层不成立 |
| 明确 > 含糊 | 在**关键 magic number / 模型版本相关 prompt** 层面成立；不是全面属性 |
| 分层 > 单点 | 通用工程属性，**不是 Claude Code 的特征**——读者可以从其他成熟系统学到同样东西 |

## 怎么用本文档（带怀疑的读法）

1. **设计新 LLM 系统时**：从 5 个簇里挑跟你场景相关的假说，**先验证**它在 Claude Code 是不是真的成立（点进 concept 页看具体证据），再决定借鉴
2. **review 现有系统时**：用"反 Pattern 速查表"扫一遍——这部分**直接可用**，因为反 pattern 是具体的代码模式，不是抽象哲学
3. **遇到具体问题时**：通过 [[wikilink]] 跳转到 concept 页——**concept 页比本文档可信**（更接近源码）

### 哪些可以直接用

- **反 pattern 速查表**（具体到代码） — 直接抄
- **每条原则的实例段** — OBS，可信
- **每条原则的迁移配方** — 我的建议，验证后用

### 哪些要带怀疑

- **5 个簇的标题** — 我的分类，可能不是 Claude Code 的内部结构
- **每条原则的"论点"句** — 我的提炼，可能过度归纳
- **元假说和 3 条贯穿线** — 最高 NARR 风险，最 quotable，最可能误导

### 哪些不要直接用

- **"Claude Code 这样所以你也该这样"的隐含逻辑** — 单用户开发工具的设计选择不一定迁移到多用户业务系统
- **"这是哲学"的 framing** — 把它降级为"一种观察到的模式"
- **3 条贯穿线作为 Claude Code 的辨识特征** — 至少线 3（分层）是通用属性

跟具体 concept 页的关系：

```
本文档（提炼层）
    │
    │ 引用具体实例
    ▼
24 篇 concept 页（设计层）
    │
    │ 引用源码
    ▼
restored-src/（实现层）
```

三层都需要——本文档是杠杆最高的入口，concept 页是设计细节，源码是最终事实。
