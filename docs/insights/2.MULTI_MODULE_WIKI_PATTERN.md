# 多模块 LLM Wiki 模式 — Karpathy 模式在跨模块仓库的延伸

> 沉淀来源：2026-05-19 在 leto-ai（4 模块仓库）反复推演 Karpathy LLM Wiki 模式后得到的真实经验。
> 与 [1.LLM_WIKI_PATTERN.md](1.LLM_WIKI_PATTERN.md) 的关系：那篇是单 wiki 模式的总结，本篇是把它推广到多模块、多人协作场景时遇到的问题与最佳实践。

---

## 一、为什么需要多模块 wiki 模式

### Karpathy 模式的隐含假设

Karpathy 描述的 wiki 形态优雅，但有四个隐含前提：

1. **单人维护** — 一个人策展一个知识库
2. **单领域** — 个人成长 / 一个研究主题 / 一本书
3. **高频查询** — 每天都用，复利成立
4. **文档归属一元** — 所有 wiki 内容都归我

### 多模块仓库的真实场景

工程仓库往往违反这四条：

| 维度 | Karpathy 默认 | 多模块仓库 |
|---|---|---|
| 维护者 | 1 人 | 多人，甚至跨团队 |
| 领域 | 单一 | 每模块独立技术栈 + 业务概念 |
| 查询频率 | 高 | 模块间不均（有的天天用，有的从不查） |
| 归属 | 全归我 | 自己的 / 同事的 / 历史遗留的混杂 |

**直接套用单 wiki 模式会出问题**：试图把别人的文档纳入自己的 wiki，导致改造范围爆炸；试图让所有模块的 wiki 都同样丰富，导致冷模块的 wiki 永远填不满。

## 二、核心发现：边界先于结构

经几轮迭代得出的最关键认知——**先确定"什么不归我管"，再设计 wiki 结构**。

### 2.1 用户域 vs 别人域

仓库下的 markdown 不是同质的。常见归属类型：

- **用户域**：你/你的协作 LLM 写的，归你维护
- **别人域**：同事或外部团队维护，你不动
- **孤儿域**：历史遗留无人维护，碰它就接锅

**关键决策**：只对用户域做 wiki 改造。别人域作为 Raw Sources 视角的"只读参考"，不重组、不改名、不删除。

### 2.2 单模块边界 vs 跨模块边界

Karpathy 单 wiki 没这个问题。多模块下：

- LLM 在单模块工作时不应主动加载其他模块上下文（噪声）
- 跨模块查询要走显式"升级路径"
- 边界必须在 Schema 层（CLAUDE.md）声明，不能靠隐式习惯

## 三、三层结构（多模块版）

| 层 | 单 wiki 形态 | 多模块形态 |
|---|---|---|
| **Schema** | 一份 CLAUDE.md | 递归加载（根 CLAUDE.md + 模块 CLAUDE.md） |
| **Wiki** | 一个 markdown 集合 | 每模块独立 wiki + 跨模块薄层 |
| **Raw Sources** | 原始文档目录 | 别人域 docs/（只读参考） |

物理布局示例：

```
repo/
├── docs/                       ← 跨模块薄层（用户域）
│   ├── INDEX.md
│   └── architecture.md
├── CLAUDE.md                   ← 根 Schema
└── module-X/
    ├── docs/                   ← 别人域，不动
    ├── chuye-doc/              ← 模块 wiki（用户域）
    │   ├── INDEX.md
    │   └── log.md
    └── CLAUDE.md               ← 模块 Schema（声明边界）
```

### 紧耦合系统的变种

在事件流穿透多模块的紧耦合系统（如风控引擎 = gateway → engine → disposal → streamhouse 串联），「跨模块薄层」会自然增厚为顶层主体——例如 leto-risk 的 `docs/全链路-事件到处置.md`（465 行）和 `docs/系统全景.md`（179 行）合计占 ~640 行实质内容，且各模块 chuye-doc 的 frontmatter `related` 字段密集互引这两份。这不是滥用，是事件流穿透多模块的必然映射。**何时增厚：跨模块认知本身就是高频任务时**——具体判断依据见下文 §九 #6 耦合度准则。

## 四、十条最佳实践

### 1. 边界优先

先确定"什么是用户域"，再设计 wiki 结构。否则会陷入"试图改造别人文档"的死胡同——前期讨论中我们曾把 os 模块 73 个别人的 md 当成"待分诊清理"的硬骨头，后来澄清那不是用户域，整个改造工程量从 10-15 天降到 3 小时。

### 2. 自给自足

每模块 wiki 必须能覆盖该模块下 90% 的任务，跨模块查询是例外不是常态。否则用户在一个模块工作时被迫到处翻文档，失去模块隔离价值。

**紧耦合系统例外**：在事件流串联多模块的系统中，「模块 90% 自给自足」无法严格达到——任一事件链路 debug 都需要跨多个模块文档协同。此时应改为：**模块 wiki 提供本模块视角 + 显式 related 指向跨模块文档**（如 leto-risk 模块 chuye-doc 的 frontmatter `related` 字段密集互引 `docs/全链路-事件到处置.md` 与 `docs/系统全景.md`）。判断依据：§九 #6 耦合度准则。

### 3. 升级路径

跨模块查询走明确层级：本模块 wiki → 跨模块薄层 → 对方模块 wiki → 代码。每一步都是显式的、可被 LLM 理解的优先级。

### 4. 复利沉淀

被迫跨模块查询的结果要写回本模块的 `integration/` 子目录。下次同类问题不再跋涉——这是 Karpathy "Query 结果存回 wiki" 在多模块场景的具体应用。

### 5. 占位 ≠ 填满

建空容器 + 沉淀承诺，不要启动时强行填满。内容靠日常工作自然积累。试图在 Phase 1 就让所有模块 wiki 内容齐全是反模式——成熟的 engine/chuye-doc/ 221 文件是一年多沉淀的结果，不是产出来的。

### 6. Schema 递归加载

Claude Code 的 CLAUDE.md 递归加载机制天然支持分层 schema：从 cwd 向上递归加载所有 CLAUDE.md。利用这一点，不要重复造轮子。子模块 CLAUDE.md 写"详见根 CLAUDE.md"实际上是冗余但无害——根 CLAUDE.md 已自动在上下文。

### 7. 协议要有 anchor

单独的协议（"以后这样做"）会空转。必须配套至少一个 anchor 文件（INDEX.md），让协议指向具体目标。曾试过"先加协议，再决定是否做 INDEX"——结果协议指向不存在的 INDEX.md 大半空转。

### 8. 命名归一

所有模块用相同命名（如 `chuye-doc/`），便于跨模块跳转和工具脚本统一处理。命名分裂（一个模块叫 wiki/、另一个叫 chuye-doc/、再一个叫 internal-docs/）会让 LLM 每次都要重新推断。

### 9. 不动现状

对已有 docs 不重组、不改名、不删除。新规范只对新增文档生效。半途而废的负风险（新旧并存）比纯旧文档更糟——这条规则让改造可随时止损。

### 10. 意图导航 > 路径导航

`TAXONOMY.md`（按"我要做什么"）比 `INDEX.md`（按"文件在哪"）更有用。Karpathy 提了 index，但实践中意图层导航才是最大杠杆——它让 LLM 不需要扫描全部文件名就能定位目标。

## 五、与单 Wiki 模式的关键差异

| 维度 | 单 wiki | 多模块 wiki |
|---|---|---|
| 边界 | 隐式（一切都是我的） | **显式声明**（用户/别人/跨模块） |
| Schema | 单一 CLAUDE.md | 分层递归（根 + 模块） |
| 查询路径 | 直接搜整个 wiki | 优先级路径，按需升级 |
| 维护责任 | 一个人 | 各模块独立维护，可有人不维护 |
| 启动成本 | 渐进式即可 | **必须一次性建好骨架**（协议+anchor 配套，否则协议空转） |
| 复利来源 | 反复查询同一知识 | + 跨模块查询沉淀 |
| ROI 决定因素 | 查询频率 + 维护意愿 | + 跨模块边界是否清晰 + 用户/别人域比例 |

**最关键的一条**：单 wiki 默认"全部都查"，多模块 wiki **「不查」和「查」一样重要**——要让 LLM 知道何时停在本模块。

## 六、反模式：我们走过的弯路

### 反模式 1：试图改造所有 docs

初版方案要把根 docs、各模块 docs 全部按三层结构重组。10-15 工作日。后来发现各模块 docs 是别人维护的，不归我改。**修正**：先做归属调研，再设计范围。

### 反模式 2：启动时强行填满

试图在 Phase 1 就让所有模块 wiki 有完整内容。失败——内容是沉淀出来的，不是产出来的。**修正**：占位骨架 + 沉淀承诺。

### 反模式 3：协议没 anchor

"先加协议，再决定是否做 INDEX"——发现协议指向不存在的 INDEX.md 会大半空转。**修正**：协议和 anchor 必须配套。

### 反模式 4：方案命名爆炸

讨论中用 A/B/C/D + B-mini/B-min/B-full 表达不同方案——第三轮已经记不住每个字母对应什么。**修正**：用功能性命名（锚点/边界/索引/重构）而非字母编号；或干脆用症状命名（"找不到入口" / "跨模块加载噪声"）。

### 反模式 5：先做最小再升级

"先做 C 再决定 B"听起来稳健，实际是骑墙——C 没有 B 的 anchor 会空转。**修正**：每个档位必须是可独立终止的稳定状态，不是过渡。

### 反模式 6：忽略「Karpathy 假设是否成立」

Karpathy gist 的 ROI 之所以高，是因为他自己一个人维护自己的知识库，又是知识工作者，又每天都用。多模块多人工程仓库不一定满足这些条件。**修正**：评估前先问"我的场景符合 Karpathy 的几条假设？"

## 七、决策框架

### 7.1 适用条件

满足以下条件时多模块 wiki 模式 ROI 较高：

- 仓库有明确的模块边界（≥ 3 个独立模块）
- 你/团队会用 LLM 频繁查询代码库
- 用户域和别人域可以明确划分
- 有人愿意持续走协议（最低标准：你自己每次都遵循）

### 7.2 不适用的信号

- 仓库只有一个模块或模块间高度耦合
- 文档主要服务于代码 review 而非反复查询
- 团队不用 LLM 协作
- 没人愿意维护 wiki 的纪律
- 别人域占绝大多数（> 80%），用户域不足以支撑独立 wiki

### 7.3 核心判断准则

> **「另外的模块的人不需要看这个吗？」**
>
> - 是 → 模块级 wiki
> - 否 → 跨模块 wiki
> - 模糊 → 默认模块级，加跨模块引用

## 八、案例：leto-ai 仓库实施记录

### 输入

- **仓库**：4 模块（Python engine + Java gateway/os/business）
- **文档量**：~270 md，分布严重不均（engine 178、os 73、gateway 15、business 2）
- **用户域**：根 docs/（1 文件）+ engine/chuye-doc/（221 文件，已成熟）
- **别人域**：4 个模块各自的 docs/

### 决策点

1. engine/docs/ 是别人域 → 不动
2. engine/chuye-doc/ 已成熟（含 INDEX/TAXONOMY/log/HANDOFF/frontmatter 标准）→ 直接用作其他模块基准
3. 占位骨架 + 协议 = 完整方案，不需要"分阶段渐进"

### 落地（11 个动作，实际约 3h）

```
根目录（2 项）
[x] 新建 docs/INDEX.md
[x] 修改 CLAUDE.md 追加文档维护协议

4 模块 CLAUDE.md 加查询协议（4 项）
[x] engine / gateway / os / business 各加协议段

3 模块新建 chuye-doc 占位（3 项 × 2 文件）
[x] gateway / os / business 各新建 INDEX.md + log.md
```

### 演化路径（讨论时间线）

1. **初版**：三层物理结构，全模块改造（10-15 工作日）
2. **ROI 反思**：成本被低估、收益被高估，推荐"先做协议再观察"
3. **B vs C 评估**：发现 C 单独空转、B 与 C 配套
4. **边界澄清 1**：engine/docs/ 是别人的可忽略
5. **边界澄清 2**：所有模块 docs/ 都是别人的，新建 chuye-doc/
6. **最终**：3-3.5h 落地，纯新增不动别人

每一轮的核心动作都是**进一步澄清边界**，而非细化结构。这印证了"边界先于结构"。

## 八·2、案例 2：leto-risk 7 模块紧耦合系统

### 输入

- **仓库**：7 模块 Java/Maven workspace（engine / server / gateway / disposal / streamhouse / meta / plugin），无聚合 POM，每模块独立 Maven lifecycle
- **耦合形态**：事件流穿透（gateway → engine → disposal → streamhouse，plugin 进程内嵌）+ 配置流（server 写 → meta starter 推 → 4 runtime 订阅）
- **文档量**：用户域分布——根 `docs/`（4 份：INDEX / log / 全链路 / 系统全景）+ 7 模块各自 `chuye-doc/` + 遗留用户域散布（`leto-engine/ARCHITECTURE.md` 1261 行、`leto-server/结构理解.md`、`leto-engine/leto-engine-indi-ANALYSIS.md`、`leto-plugin/README.md`、各模块 CLAUDE.md）
- **用户域 vs 别人域**：遗留用户域留在原位，通过 `chuye-doc/INDEX.md` 登记访问；别人域 `<模块>/docs/` 不动

### 决策点

1. **紧耦合识别**：7 模块按事件流串联 + 配置流分发，跨模块认知是主任务而非例外。Karpathy 单 wiki 假设、leto-ai 「90% 模块自给自足」假设，在此处都不严格成立。
2. **跨模块薄层主体化**：`docs/全链路-事件到处置.md`（465 行）+ `docs/系统全景.md`（179 行）成为顶层主体，模块 chuye-doc 提供详细补充并通过 `related` 字段反向引用。这与 leto-ai 「跨模块薄层 = 1 份薄文档」形成鲜明对比。
3. **遗留主权威保留**：`leto-engine/ARCHITECTURE.md`（1261 行）这类一年多沉淀的主文档不重写，模块 chuye-doc 自我定位为「补充而非替代」（engine `chuye-doc/architecture/overview.md` 开头明确声明），避免重复造轮子。

### 落地

- **一日内集中沉淀**：2026-05-22 当日 7 模块 chuye-doc 同时从占位骨架推进到实质内容。比 leto-ai 当年的渐进式更激进——因为紧耦合下的「凝结效应」需要 5+ 模块凑齐才能浮现整体认知（参见 leto-risk `docs/log.md` line 17、19 的"跨模块洞察"条目）。
- **spec retroactive 补齐**：先动手写文档，再发现 frontmatter 9 字段标准、log 行格式等 leto-ai 已有 spec 没顺手查（§十一·真实事故段即此案例），事后补齐。
- **内容准确性纪律沉淀成 6 条规则**：多次自审纠错（数字编造 13+9=22 实数 19、`head -30` 截断未补 `wc -l`、"唯一中心"措辞过度等）后，把教训提升到根 `CLAUDE.md` 协议层：6 条规则（数字必须实数 / 行为归因必须 grep / 命名推断必须 hedge / 绝对量词前想反例 / catch 块读完整 / 不写百分比）+ Closing Checklist 加 1 项「内容准确性」。这是 pattern doc 的延伸贡献，不是 pattern 本身。

### 关键差异（对比 leto-ai 案例）

| 维度 | leto-ai（松耦合） | leto-risk（紧耦合） |
|---|---|---|
| 跨模块薄层 | 1 份薄文档 | 2 份顶层主体（系统全景 + 全链路）合计 ~640 行 |
| 模块 wiki 自给自足 | 90% 可达 | 紧耦合下不严格成立，靠 `related` 字段密集互引 |
| 遗留用户域 | 较少 | 较多（ARCHITECTURE.md / 结构理解.md / 模块 CLAUDE.md 等原位保留 + chuye-doc 补充） |
| 内容准确性纪律 | 渐进 | retroactive 多次自审纠错沉淀成 6 条规则（根 CLAUDE.md） |
| 沉淀节奏 | 渐进式 | 一日内集中（紧耦合的凝结效应需 5+ 模块凑齐才浮现） |

### 启示

紧耦合系统并不否定多模块 wiki 模式，而是要求模式参数化：**「跨模块薄层 vs 顶层主体」「90% 自给自足 vs related 互引」是耦合度连续谱的两端，不是非此即彼**。判断耦合度走 §九 #6 准则。

## 九、6 个判断准则速查

| # | 准则 | 用法 |
|---|---|---|
| 1 | **归属** | 归我维护吗？是 → 用户域；否 → 别人域不动 |
| 2 | **位置** | 另外的模块的人需要看吗？是 → 跨模块；否 → 模块内 |
| 3 | **沉淀** | 被迫跨模块查询了吗？是 → 写回本模块 integration |
| 4 | **生效** | 协议指向的 anchor 存在吗？否 → 先建 anchor 再加协议 |
| 5 | **存活** | 3 个月没新增文件？是 → 这个 wiki 不需要存在，删掉 |
| 6 | **耦合度** | 模块间是否事件流串联？是 → 紧耦合，跨链文档主体化（§八·2）；否 → 松耦合，跨链薄层（§八） |

## 十、与 Claude Code 机制的契合点

多模块 wiki 模式之所以可落地，依赖 Claude Code 的几个机制：

| Claude Code 机制 | 在多模块 wiki 中的角色 |
|---|---|
| CLAUDE.md 递归加载 | 让分层 Schema 自动生效，不需手动指定加载顺序 |
| Read 工具 | 兜底——即使递归加载失败，子模块协议中的相对路径也能被主动 Read |
| 子 Agent / Explore | 跨模块查询时启动子 Agent 隔离上下文，避免污染主对话 |
| Memory 系统 | 沉淀会话级洞察到 wiki 的桥梁——memory 是临时的，wiki 是持久的 |

这些机制是 Karpathy 写 gist 时还不存在的（gist 早于 Claude Code 普及）。多模块 wiki 模式实际上是**"Karpathy 模式 × Claude Code 机制"的乘积**，不是对 Karpathy 的简单拓展。

## 十一、pattern 不等于 spec

这篇文档是 **pattern-level**：讲心智模型——为什么需要边界、什么时候适用、反模式有哪些。它故意不写死操作细节（字段名、log 格式、checklist 项），因为 pattern 要能跨仓库复用，而那些细节是仓库本地约定。

### 落地必须配 spec

落到具体仓库时**必须配套 spec-level 文档**，通常写在该仓库根 `CLAUDE.md` 的「文档维护协议」段。spec 应包含至少这 5 项：

- **frontmatter 字段清单**（字段名 + MUST/SHOULD + 含义）
- **log 行格式**（如 `YYYY-MM-DD | 操作 | 路径 | 说明`）
- **Closing Checklist**（每次新建/修改文档收尾必查项）
- **cascade 规则**（用户域内连带改动如何记 log）
- **别人域豁免条款**（允许触达 `<模块>/docs/` 的具体情形）

leto-ai 仓库 `CLAUDE.md`「文档维护协议」段是参考实现，新仓库照搬调整即可。

### 真实事故：2026-05-22 leto-risk 落地

落地 leto-risk 多模块 wiki 时，执行者（Claude）只读了本 pattern doc 就直接动手，**没顺手查 leto-ai 隔壁仓库的 CLAUDE.md**——结果一次性写了 6 份模块级 + 跨链文档，**全部缺 `use_when` 字段**（按 leto-ai 协议视同未发布、LLM 检索无法命中），log 格式各不相同，cascade / Closing Checklist 完全没建立。

事后补救成本不大（retroactive 加 frontmatter），但揭示了 pattern doc 的一个改进点：**应当显式指向 spec 配套**，否则下一个落地者大概率重复同样的错。这就是本节存在的原因。

### 反过来：写 pattern doc 时

如果你正在沉淀一篇 pattern doc（如本文），记得在末尾留一句"本 pattern 落地需配套 X 类型的 spec，参考 Y"。**沉淀者把"显然的事"留在脑子里是经典盲点**——你觉得显然的"frontmatter 字段就那 9 个"，对没经历过的读者（包括未来 LLM）绝不显然。

通用规则：**pattern doc 必须显式指向 spec 配套位置**，pattern + spec 才是完整套件。只交付 pattern 等于交付一半。
