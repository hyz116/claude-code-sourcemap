# 自我批判：研究方法论的失败模式

> 4 轮自我批判后浮现出的**研究方法论问题**——我（一个外部研究者用 LLM 辅助阅读源码）在写 24 篇 concept 页 + 1 篇 insights 文档时反复犯的归纳偏差。本文档记录这些偏差**怎么发生的、长什么样、怎么识别和避免**。
>
> 目标读者：
> 1. **未来的我**——再做类似研究时避免同样错误
> 2. **未来读者**——理解本 wiki 的可信度结构
> 3. **想用 LLM 做自动化研究的其他人**——这种偏差是 LLM 辅助研究的系统性问题

---

## 4 轮自我批判的发现汇总

| 轮次 | 对象 | 发现 |
|---|---|---|
| 1 | [[prompt-cache-editing]] | 从 client 代码反推服务端行为，把单一信号的 SPEC 反复当 OBS 写。"per-request transient" 在页面里出现 5 次都是断言 |
| 2 | [[ground-truth-via-tools]] | 把"消息历史不可伪造"包装成"防幻觉根哲学"。声称"所有其他防幻觉机制都是这条的应用"——审计后发现 7 篇里只有 2-3 篇真派生 |
| 3 | [[2.DESIGN_PRINCIPLES]] | 整本 wiki 的提炼层是同样问题的高阶版本。元论点和"3 条贯穿线"是叙事压扁——线 3"分层 > 单点"其实是任何成熟系统都有的属性 |
| 4 | 簇分组本身 | 我归纳的 7 个簇里 2 个是过度归纳——"防幻觉簇 7 篇"实际是 4 个子主题，"权限/Mode 簇 4 篇"是目录驱动归纳（coordinator-mode 跟权限关系弱） |

**累积修改的方向全是单向的**：降级 framing、剥掉叙事、降低断言强度。**没有一次修法是补充新内容**——全部是**剥过度叙事**。这意味着研究的"结论"层比看起来的少，"观察"层才是真正可信的部分。

## 9 类具体归纳偏差（带 signature 和修法）

### 1. 单一信号当事实

**Signature**：从一个观察推断一个机制，反复以"事实"形态写出来。

**例**：[[prompt-cache-editing]] 里 "deletion 是 per-request transient" — client 代码每轮 re-send → 我推断"服务端 cache 不变"——但 4 种解释都跟 client 行为兼容。

**修法**：每个推断都列**替代解释表**。如果只能想出一种解释就警觉——是不是没努力想反例？

### 2. 多机制归纳为"根哲学"

**Signature**：看到 N 个独立机制都符合某 pattern → 包装成"统一原则" / "根哲学" / "贯穿线"。

**例**：[[ground-truth-via-tools]] 把 6 个机制（read-before-write / task-notification / 大输出溢出 ...）归纳为"防幻觉根哲学"。审计后只有 2-3 个真派生。

**修法**：起完"根哲学"名字后，**强迫自己列反例**——所有相关页都符合吗？哪些是互补 / 正交 / 矛盾？

### 3. 编故事填补观察空白

**Signature**：看到一个机制 → 编"为什么这样设计"的解释。**没有证据**说设计师是这样想的。

**例**：
- "为什么不让服务端记住？**因为 prompt cache 被设计为 stateless**"——纯编
- "**纯洁主义** / **免费的强约束** / **信息密度优于防御性**"——格言化包装

**修法**：每个"为什么这样设计"问"我有证据吗？还是在编？" 没证据就标 NARR 或删掉。

### 4. 过度对立化框架

**Signature**：把两种方案夸张成对立立场。

**例**：[[ground-truth-via-tools]] 的"事前隔离派 vs 事后验证派"——leto-ai 跟 Claude Code。审计后发现两边都用全部 4 层，只是**重心不同**，不是对立。

**修法**：起"X vs Y 派"的对照表前问"它们真的对立吗？还是只是侧重不同？"

### 5. Implementation choice 包装成"设计原则"

**Signature**：代码里一个具体选择（一行 if、一个 throw）被升级为"原则"。

**例**：[[coordinator-mode]] 里 "agent context 不能切 plan" 我列为原则，但代码里就一个 throw——可能只是**没考虑这个 case** 而非有意设计。

**修法**：每条"原则"问"如果这只是 implementation choice 而非 principle 呢？" 那就降级为"observation"。

### 6. 通用属性当作系统特征

**Signature**：把任何成熟系统都有的属性列为 Claude Code 的"贯穿线"。

**例**：[[2.DESIGN_PRINCIPLES]] 线 3 "分层 > 单点"——任何 banking app / OS / web service 都符合。作为 Claude Code 的辨识特征价值不高。

**修法**：每个"特征"问"其他成熟系统也这样吗？" 是 → 不是 Claude Code 特征。

### 7. 目录驱动归纳

**Signature**：把文件目录靠近的页归到一个簇——但概念上不一致。

**例**："权限/Mode 簇 4 篇"把 coordinator-mode 和 plan-verification-handoff 归入——它们跟权限关系弱，归一起是因为目录靠近 + 都是"工作流相关"。

**修法**：分簇前问"这个簇的概念定义是什么？每页都真符合吗？" 不符合的拆出来。

### 8. 服务端从 client 反推

**Signature**：当一个组件不可见（服务端、DCE 掉的代码、内部系统），从可见组件的行为反推。

**例**：[[prompt-cache-editing]] 整页大半是从 client 代码推 server 行为；术语解读"Mycro = Anthropic 推理引擎"是基于 page_manager/index.rs 这个文件路径推的。

**修法**：涉及不可见组件时明确标 SPEC，列替代解释。**不可见 = 不可知**，不要假装能看到。

### 9. "碰巧符合"当作"有意为之"

**Signature**：多个机制都符合某 pattern → 假设设计师**有意识**用这个 pattern。

**例**：6 个机制都让模型不能伪造事实 → 我归纳为"统一哲学"。但实际可能是 API 设计副产品（角色限制）+ 各自独立加的具体机制——**没有人在写代码时引用这个原则**。

**修法**：把"X 是 Claude Code 设计师有意为之的原则"改成"X 是观察到的一致性模式"——后者诚实，前者是创造叙事。

## 抽象阶梯：同种错误在 4 个层级出现

最深的发现：归纳偏差在**多个抽象层级**重复出现，每往上一层就失真更多。

```
Layer 0: 源码（事实层）
   │
   │ 我归纳
   ▼
Layer 1: 单机制描述（OBS 多）   ← 大部分 concept 页 70% 内容在这层
   │
   │ 我归纳
   ▼
Layer 2: 单页"设计原则"段（NARR 多）   ← 每页底部"设计原则"表
   │
   │ 我归纳
   ▼
Layer 3: 簇分组（"防幻觉簇 7 篇"）   ← 索引层
   │
   │ 我归纳
   ▼
Layer 4: 元论点 / 贯穿线 / 哲学（最高 NARR）   ← DESIGN_PRINCIPLES 顶部
```

**信任度从底向上递减**。Layer 0 是事实，Layer 4 是叙事。**每一层都是上一层的归纳，每次归纳都丢一些精度**。

我反复犯同一种错误的不同层级版本：

| 层级 | 错误形态 |
|---|---|
| Layer 1 | 把单个观察当事实（如"deletion 是 per-request transient"）|
| Layer 2 | 把多个观察归纳成"原则" / "philosophy" |
| Layer 3 | 把多页归到一个簇并起统一标签 |
| Layer 4 | 把多簇归纳成"贯穿线"和"元论点" |

**修法不是修单层**——是认识到每往上一层都需要更高的怀疑度。

## 给读者的可信度排序

读 wiki 时按这个顺序倒着 sanity check：

```
代码引用（带行号）            ★★★★★
   ↓
OBS 段落（事实陈述）           ★★★★
   ↓
INF 段落（多信号支持的推断）   ★★★
   ↓
SPEC 段落（单信号推断）        ★★
   ↓
NARR 段落（叙事化包装）        ★
```

跟文档类型的对应：

```
具体 concept 页的"在 Claude Code 中的体现"段          → 多 OBS / INF
具体 concept 页的"设计原则"表                         → 多 NARR / OBS+NARR
具体 concept 页的"可迁移性"段                          → 多我的建议
DESIGN_PRINCIPLES 的"实例"段                           → OBS（可信）
DESIGN_PRINCIPLES 的"论点 / 直觉 / 迁移配方 / 反 pattern" → NARR
DESIGN_PRINCIPLES 的"元论点 / 3 条贯穿线"              → 最高 NARR
```

**最 quotable 的部分通常是最不准确的部分**。"24 篇 concept 页提炼出的核心哲学"是 marketing line，不是研究结论。

## 写作检查清单（10 条）

每写完一段，问自己：

1. **每条断言我都能定位到代码引用吗？** 不能就标 SPEC/NARR
2. **当我说"X 是 Y 的设计原则"时，有 Anthropic 的依据吗？** 没有就改成"是我观察到的模式"
3. **当我说"所有 X 都遵循 Y"时，反例呢？** 找不到反例就警觉——是不是反例没去找
4. **当我起 quotable 名字时，准确性是不是被牺牲了？** "Information density > defensive" 听起来很好，但说清楚了什么吗
5. **当我对比"X 派 vs Y 派"时，他们真对立吗？** 还是只是侧重不同
6. **当我列"原则" / "哲学" / "贯穿线"时，是 Claude Code 特征还是任何系统都有？** 后者就降级
7. **当我把 implementation choice 升级为 principle 时，可能只是 implementer 没考虑别的 case 吗？**
8. **当我从 client 代码推服务端行为时，我标了 SPEC 吗？** 列了替代解释吗
9. **当我把 N 个机制归到一个簇时，每个机制都真属于这个簇吗？** 还是借了标签
10. **当我写下一个看起来很 quotable 的"洞察"时，是不是已经污染了准确性？**

最后一条最难——**好句子比准确句子传播更广，写作时无意识偏向 quotable**。每次发现自己写出"听起来深刻"的句子，要专门检查它是不是过度叙事。

## 这种偏差为什么会发生（认识论原因）

5 个驱动因素：

### 1. 研究者偏差（confirmation bias）

寻找模式 → 自然会找到模式。我开始写"防幻觉簇"后，每读一篇新机制都倾向**看出它跟防幻觉的关系**。后来发现的"7 篇里只有 2-3 篇真派生"是因为最后才回头审计的。

### 2. 故事压缩（narrative compression）

为了让 wiki 易读，把零散信息压缩成连贯叙事。**压缩 = 选择性丢失**——丢的就是"反例 / 削弱 / 矛盾"那些不易讲故事的部分。

### 3. Quotable 拉力（quotability gradient）

"物理约束 > prompt 约束"比"在某些子系统里架构强制比 prompt 提示更可靠，但其他子系统反向"传播性强 100 倍。**写作者在选词时无意识偏向 quotable**——这是修辞学陷阱，不是数据问题。

### 4. 缺反馈循环（no peer review）

整个 session 是单向的。没有人挑战我的归纳。没有 reviewer 说"这条原则的反例是什么？" 归纳偏差**累积无人察觉**。

### 5. 抽象阶梯压力（abstraction ladder）

Layer 1 已经是源码的归纳；Layer 2 是 Layer 1 的归纳；Layer 3 是 Layer 2 的归纳。**每层都看起来"在做有用的提炼"**，但失真累积。读者看 Layer 4 时感觉"这是综合 24 篇的精华"——其实是经过 4 次失真的 NARR 堆叠。

## 给未来研究者的建议

如果你想用 LLM 辅助做类似的源码研究（提炼一个系统的设计模式）：

1. **先约定标签语言**：OBS / INF / SPEC / NARR——写每段时就标注，**不要事后审计**（成本高 5×）
2. **每章末尾自问"反例呢？"**：强迫自己列削弱、矛盾、边界——比写"原则"清单更重要
3. **抽象阶梯每升一层就 +1 怀疑度**：Layer 1 用 80% 自信；Layer 4 不超过 30%
4. **避免 quotable 诱惑**：发现自己写出格言式句子时停下检查
5. **同步建一个"已知偏差"清单**：本文档的 9 类偏差是个起点。每发现新偏差加进去，下次写作前先 review 这个清单
6. **如果可能，找人 review**：哪怕另一个 LLM session 当 critic 也比单向归纳强。研究者偏差只能靠外部反馈打破
7. **接受"碰巧符合"是真实情况**：不是每个 pattern 都有故事；多个独立工程决策可以**碰巧对齐**，不需要一个统一意图

## 最后一句

24 篇 concept + 3 篇 insights 是个**可观的研究产出**，但读者**应该把它当作"一个外部研究者的事后归纳记录"，不当作"Claude Code 设计圣经"**。

具体可信的部分（OBS、代码引用、行为描述）远多于不可信的部分（原则、哲学、贯穿线），但**写作的修辞偏向把后者放在最显眼处**——读者要主动调整重心。

本文档的存在本身就是这种调整的尝试：把 wiki 的认识论结构**显性化**，让读者跟我自己都更诚实地使用它。
