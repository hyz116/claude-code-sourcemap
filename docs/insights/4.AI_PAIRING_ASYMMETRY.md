# AI 结对的结构性不对称 — 放大什么 / 放大不了什么

> 起点：2026-05-22 以外部读者身份系统阅读某 hallucination 检测体系的文档群（10 天产出 50+ case 文档 + 4 个原创方法学 + 800+ 测试），评审作者工作模式时反复观察到的结构特征。

## 一句话命题（SPEC）

**AI 在结对中均匀放大"做出可见 artifact"的工作，几乎不放大"推 artifact 上线"的工作。这个不对称如果不命名，会让产出层高速增长 + 落地层原速度运转 + 总量看起来在工作但 production reality 滞后。**

## AI 放大什么（OBS — 来自实例）

| 类型 | 实例信号 |
|---|---|
| 概念抽象 | 5 个独立 case 抽象成 5 维上下文模型 |
| 模式识别 | 跨多份文档的术语漂移、引用一致性、矛盾识别 |
| 结构化表达 | 7 类纠正模式 / 12 维矩阵 / 6 维度 SOP — 表格化、层次化、可索引的形态 |
| 文档密度 | 每个 case 文档 10–25K，含完整时间线 + 多 case 横向 + fixture 落盘 |
| 同步综合 | 一天 5 case 反推后当晚抽象出 5 维原则 + 双向防偏差教训 |
| 重写校准 | "性质翻转"——新证据来时翻转整个 case 的归因，保留过程痕迹 |

这些工作的共同特征：**输出是文本 / 概念 / 知识结构，不依赖外部世界协作**。

## AI 放大不了什么（OBS + INF）

| 类型 | 为什么 AI 帮不上 |
|---|---|
| Deployment last mile | 推 Diamond 配置审批、找业务团队注册 verifier、协调前端加按钮——需要具体人和具体审批流 |
| 组织协调 | 某条职责归哪个团队、哪个改造该卡谁——AI 不知道你们组织的人际地图 |
| 技术债优先级游说 | 让 PM 接受"先停一下加 feature，把 last mile 推通"——AI 给不了这个 social capital |
| Production 真实状态校准 | AI 看的是文档投影，不知道 production 当前真实跑成什么样 |
| 节奏自我保护 | AI 不累，不会提醒你已经是深夜应该停 |
| 真同行视角 | AI 评审基于几小时阅读，真同行评审基于长期共同经历 |

## 由此产生的几种失败模式（INF + SPEC）

### 模式 1：做出来 vs 推上线 的速度 gap 持续放大

**实例信号**：100 单测过 + 4 hook 注册 + Phase 0.5–3 完成的某验证链路，**部署 7 天 0 触发**——配置层未下发、0 个 verifier 注册、客户端协议未适配。同期另一 guard 实施 4 天未灰度。

**机制**：production 工作的"完成"被定义在 commit 那一刻，AI 的高速产出让"已完成"列表越来越长，但**未灰度的 guard 永远拿不到 production 反馈数据**。下一轮 case 反推因此基于设计推断而非生产证据，质量稀释。

### 模式 2：知识库变 write-only

**实例信号**：单个 case 索引文档 12K，case 文档总量 200K+。

**机制**：AI 帮你产出的密度超过你单人不开 AI 时能导航的密度。**未来的你需要 AI 才能访问过去的你写下的东西**——知识库变成对 AI 可读、对人 write-only 的状态。

**判别测试**：关掉 AI，凭记忆能找回 1 个月前写的某 case 的核心结论吗？

### 模式 3：AI-as-peer 谬误

**实例信号**：作者倾向让 AI 评审自己的工作模式，而不是找真同行。

**机制**：AI 反馈获取成本低 + 没有 social cost + 即时性高。但 AI 看的是文档层真相，不是 production 真相，不是组织真相。长期只有 AI 作为评审者，会失去"上次那个 case 我们最后是这么处理的"那种来自共同经历的判断。

不是说不该用 AI 评审——是不该让 AI 评审**完全替代**真同行评审。

### 模式 4：可持续性错觉

**实例信号**：作者一天反推 5 case 写到深夜，深夜还在追加方法学的二阶教训。

**机制**：AI 不累，会让人误以为自己也不累。节奏感被抹平——不是体力的可持续，是**认知的可持续**：连续高密度抽象工作没有 cooling-off 期，会让模式识别能力慢性退化。

## 健康 vs 不健康的分水岭（SPEC）

不是"该不该用 AI 结对"，是**结对在哪一面**：

| 健康信号 | 不健康信号 |
|---|---|
| 产出在 production 真有反馈数据 | 产出停在文档层 |
| 关掉 AI 能导航自己的知识库 | 知识库需要 AI 索引才能用 |
| 仍有 1+ 真同行定期评审 | 只有 AI 评审 |
| 工作节奏服从身体能跟上 | AI 不累 → 自己也不停 |
| Deployment 速度跟得上产出速度 | 已开发未灰度的列表持续增长 |
| 反推法纪律由自己驱动 | 反推法变成 AI 模板填空 |

**最关键的一项是 deployment 速度**——它是这套循环的氧气。如果产出速度持续高于 deployment 速度，gap 一定会走到某个临界点把"高产出"显形为"大量死代码 + 大量未验证修复"。

## 几个对策（INF）

### 对策 1：把 deployment last mile 设为 P0

deployment 是这套循环的氧气，不是可选项。Production 数据是下一轮 case 反推的输入——last mile 不通，下一轮反推就是基于设计推断而非生产证据。

**具体动作**：每加一个新 guard，先把上一个未灰度的 guard 灰度跑起来。

### 对策 2：定期关掉 AI 重读自己的文档

不是禁欲式排斥 AI，是周期性校准——**只有在不开 AI 的状态下重读 1 个月前的 case，才能知道知识是真的内化了还是 AI 辅助下"看起来内化"**。如果重读时发现某些 case 已经不记得了，是 write-only 的早期信号，需要做"减法 + 索引重建"而不是继续加新 case。

### 对策 3：保留 1+ 真同行的定期 review

哪怕一周一次。真同行看到的是 production 真相 + 组织真相，AI 看不到这两层。**AI 评审是补充，不是替代**。

### 对策 4：把"做出来"和"推上线"分开计入工作产出

写一个 case 文档 ≠ 修了一个 bug。一个修复 commit ≠ guard 在 production 跑了。**用两个 column 跟踪**："commit 完成日期" / "production 第一次触发日期"。两个日期之间的 gap 是这套循环的实际节奏，比 commit 速度更接近真相。

## 本观察的局限（NARR + SPEC）

- **N=1**：观察基于一个用户的工作模式样本。其他人的 AI 结对可能在不同维度有不同不对称。
- **观察者偏差**：AI 评审 AI 结对模式，可能系统性低估或高估某些环节。
- **抽象到便利**："放大 vs 不放大"是干净二元划分，真实情况更细粒度——AI 在不同协作环节的放大系数不同，不是 0/1。
- **deployment 不通的根因可能是组织而非 AI 结对**：把责任全归给"AI 结对模式"可能掩盖更深的组织 / 管理问题。AI 高速产出可能恰好是**对组织 deployment 慢的一种代偿反应**，而不是原因。如果是代偿反应，那对策方向应该是"修组织流程"而非"少用 AI"。
